# Инструкция по работе с Telegram-ботом

Бот — рабочий интерфейс системы измерения маркетинга «Поступашек». Через него маркетолог создаёт рекламные размещения и получает отчёты, клиент переходит по рекламной ссылке и оставляет заявку, а менеджер фиксирует оплату.

> Бот не принимает оплату и не выдаёт доступ к курсам. Продажа по-прежнему проходит через менеджера. Задача бота — связать рекламное размещение, действия пользователя, заявку и оплату.

## 1. Роли

### Маркетолог / администратор

Работает с рекламными размещениями и аналитикой:

- создаёт новое размещение;
- получает уникальную tracking-ссылку;
- смотрит список размещений;
- проверяет воронку, CPA и ROMI;
- сравнивает модели атрибуции;
- проверяет полноту данных;
- при необходимости загружает исторические продажи.

Основная точка входа — команда `/menu`.

### Клиент

Переходит в бот по уникальной ссылке из рекламного размещения.

Бот фиксирует источник входа, после чего пользователь может посмотреть направления и курсы и оставить заявку.

### Менеджер

Получает заявку, связывается с клиентом и проводит продажу. После оплаты менеджер отмечает её в боте, чтобы заказ попал в measurement system.

## 2. Перед запуском

Установите зависимости:

```bash
pip install -r requirements.txt
```

Создайте `.env` из примера:

```bash
cp .env.example .env
```

Заполните основные настройки:

| Переменная | Для чего нужна |
|---|---|
| `BOT_TOKEN` | токен Telegram-бота |
| `ADMIN_IDS` | Telegram ID пользователей с доступом к админ-панели |
| `MANAGER_CHAT_ID` | чат, куда бот отправляет заявки |
| `MANAGER_IDS` | пользователи, которым разрешено фиксировать оплаты |
| `MANAGER_USERNAME` | username менеджера/менеджеров |
| `HASH_SALT` | секретная соль для хеширования идентификаторов |
| `ACQUIRING_RATE` | комиссия эквайринга, например `0.03` |
| `ATTRIBUTION_WINDOW_DAYS` | окно атрибуции; по умолчанию 30 дней |

Запуск:

```bash
python -m bot.main
```

SQLite-база создаётся автоматически при первом запуске. `.env` и рабочую базу с пользовательскими данными не нужно коммитить в GitHub.

## 3. Типовой сценарий работы маркетолога

### Шаг 1. Создать рекламное размещение

Откройте:

`/menu` → **Создать размещение**

или используйте:

`/newlink`

Бот последовательно запросит параметры размещения: метку, канал, кампанию, стоимость, дату публикации и характеристики поста.

После создания бот выдаёт уникальную ссылку.

**Важно:** для каждого отдельного размещения нужно создавать отдельную ссылку. Именно по ней система понимает, откуда пришёл пользователь.

Пример бизнес-логики:

```text
Telegram-канал A
        ↓
placement A
        ↓
уникальная ссылка
        ↓
пользователь запускает бота
        ↓
touch A
```

### Шаг 2. Использовать ссылку в рекламном посте

Разместите полученную ссылку в соответствующем рекламном посте.

Первый измеримый шаг системы — запуск бота пользователем по этой ссылке. Сам клик, после которого пользователь не нажал Start, Telegram-бот не видит.

### Шаг 3. Получить заявку

После входа пользователь может смотреть продукты и оставить заявку.

В системе появляются события воронки:

**зашёл → смотрел → оставил заявку**

Менеджер получает уведомление о заявке.

### Шаг 4. Зафиксировать оплату

После реальной продажи менеджер отмечает оплату в боте.

Для ручной записи доступна команда:

```text
/paid №_заявки сумма курсы
```

После этого появляется заказ, связанный с заявкой и, если источник известен, с рекламным касанием.

### Шаг 5. Посмотреть результат рекламы

Используйте:

`/report`

В отчёте по каждому размещению показываются:

- сколько пользователей зашло;
- сколько посмотрело продукт;
- сколько оставило заявку;
- сколько оплатило;
- затраты на размещение;
- приписанная выручка;
- CPA;
- ROMI.

Пример логики отчёта:

```text
зашли  →  смотрели  →  заявки  →  оплаты
  100          60          15          5

cost: 30 000 ₽
attributed revenue: 50 000 ₽
ROMI: +66,7%
```

Числа выше — только пример, не фактический результат проекта.

---

## 4. Как читать ROMI

В системе используется:

**ROMI = (приписанная выручка − стоимость размещения) / стоимость размещения**

Например, если размещение стоило 30 000 ₽, а attribution-модель приписала ему 50 000 ₽ выручки:

```text
ROMI = (50 000 − 30 000) / 30 000 = +66,7%
```

Положительный ROMI означает, что приписанная выручка выше стоимости размещения. Отрицательный — ниже.

Если стоимость размещения равна нулю, например для собственного канала, ROMI не рассчитывается: для него имеет смысл смотреть воронку и выручку.

---

## 5. Модели атрибуции

Если перед покупкой пользователь взаимодействовал с несколькими рекламными размещениями, нужно определить, как распределить между ними выручку.

В боте реализованы четыре модели:

| Модель | Логика |
|---|---|
| `last` | 100% выручки получает последнее рекламное касание |
| `first` | 100% получает первое касание |
| `linear` | выручка делится поровну между касаниями |
| `position` | больший вес получают первое и последнее касания |

Базовое окно атрибуции — **30 дней**.

Также действуют два важных правила:

1. После покупки старые рекламные касания не получают credit за следующую покупку этого клиента.
2. Если подходящих рекламных касаний нет, продажа относится к **Organic/Direct** и не теряется из отчёта.

Модели можно сравнивать через отчёты. Если вывод о размещении сильно меняется при смене модели, решение по нему менее устойчиво.

> Attribution — это оценка распределения уже произошедших продаж. Она не доказывает, что покупка произошла именно благодаря рекламе.

## 6. Основные команды

| Команда | Что делает |
|---|---|
| `/menu` | открывает панель управления |
| `/newlink` | создаёт новое рекламное размещение и tracking-ссылку |
| `/links` | показывает созданные размещения и ссылки |

| `/export` | экспортирует базу |

Примеры сравнения attribution:

```text

/report linear
/report first
/report position
```

## 7. Проверка качества данных

Перед тем как принимать решение по ROMI, используйте:

`/status`

Проверка нужна, потому что ROMI зависит от полноты исходных данных. В частности, должны быть корректно заполнены стоимость и дата рекламного размещения и сохранена связь пользователя с рекламной меткой.

Если данных недостаточно, это лучше исправить до интерпретации отчёта.

---

## 8. Загрузка исторических продаж

Историю продаж можно загрузить через:

`/import` + файл `base.xlsx` или `base.csv`.

Исторические оплаты сохраняются, но если в исходном файле нет информации об источнике клиента, бот **не придумывает attribution** для этих продаж. Они отображаются как история с неизвестным источником.

Это принципиально: система отделяет реальные известные факты от модельных оценок.

---

## 9. Что система видит и чего не видит

**Система видит:**

- рекламное размещение и его стоимость;
- пользователя, который запустил бота по tracking-ссылке;
- действия пользователя внутри бота;
- заявку;
- оплату, зафиксированную менеджером;
- связь этих событий между собой.

**Система не видит автоматически:**

- клик по Telegram-ссылке, если пользователь не запустил бота;
- переписку менеджера;
- клиента, который увидел рекламу, но написал менеджеру напрямую;
- исторический источник покупки, если его нет в исходной базе;
- купил бы пользователь продукт без рекламы.

Поэтому для новых кампаний важно проводить пользователя через tracking-ссылку и фиксировать оплату через связанную заявку.

## 10. Рекомендуемый рабочий процесс

Для каждой новой рекламной кампании:

**создать placement → получить ссылку → разместить её → собирать заявки → фиксировать оплаты → проверить `/status` → посмотреть `/report` → сравнить модели → принять решение**

Так каждое новое размещение превращается из отдельного рекламного поста в измеримый маркетинговый эксперимент.

## MVP: трекинг-бот и база измерений

Бот **не** принимает оплату и не выдаёт доступ к курсам: продажа идёт через менеджера, как сейчас.
Его задача - собирать данные, которых раньше не было.

### Роли

| Кто | Что делает | Что попадает в базу |
|---|---|---|
| Клиент | переходит по ссылке из рекламы, смотрит курсы, оставляет заявку | заход с меткой, просмотры, заявка |
| Менеджер | получает уведомление о заявке, продаёт, отмечает оплату кнопкой | заказ и курсы в нём |
| Админ | заводит размещения через `/newlink`, смотрит отчёты | канал, стоимость, дата, тип поста |

### Структура кода

```
bot/main.py            обработчики Telegram: меню курсов, заявки, оплаты, панель админа
core/db.py             схема SQLite и функции записи (единственное место с SQL)
core/attribution.py    правила атрибуции, воронка, ROMI
core/catalog.py        курсы, направления, пакеты
core/importer.py       импорт base.xlsx в fact_order
core/quality.py        проверка полноты данных для /status
core/config.py         настройки из .env
data/schema.sql        структура таблиц (сама база создаётся при первом запуске и в репозиторий не созпаняется)
```

### База данных

Всё хранится в `data/bot.db` (SQLite), файл создаётся автоматически при первом запуске.
Справочники с префиксом `dim_`, факты — с `fact_`.

| Таблица | Что хранит | Кто заполняет |
|---|---|---|
| `dim_placement` | размещение: метка, канал, кампания, тип поста, скидка, стоимость, время публикации | админ, `/newlink` |
| `dim_user` | пользователь: хеш Telegram ID, хеш username, когда и по какой метке пришёл | бот |
| `fact_touch` | заход в бота: кто, по какой метке, когда | бот |
| `fact_bot_event` | что смотрел: направление, курс, пакет | бот |
| `fact_lead` | заявка: интерес, ответ «откуда узнал», время, менеджер, статус | бот и менеджер |
| `fact_order` | оплата: сумма, эквайринг, время, связь с заявкой | менеджер или импорт base.xlsx |
| `fact_order_item` | курсы внутри заказа, чтобы не терялись пакеты | вместе с заказом |
| `fact_attribution` | кому приписана выручка: модель, доля, сумма | пересчитывается при `/report` |

Вся система держится на двух связях:

- `fact_touch.placement_id -> dim_placement` — из какой рекламы пришёл человек;
- `fact_order.lead_id -> fact_lead -> fact_touch` — какая реклама закончилась деньгами.

Пустое значение тоже несёт смысл: пустой `placement_id` означает «пришёл сам», пустой `lead_id` -
«старая продажа из base.xlsx, источник неизвестен». В отчёте это отдельные строки, а не общая куча.

Бот записывает данные не напрямую: обработчики вызывают функции из `core/db.py`
(`add_touch`, `create_lead`, `add_order` и другие), которые выполняют `INSERT` с подстановкой
значений через `?` и сразу фиксируют результат командой `commit()`.

**Приватность.** Telegram ID и username хранятся только в виде хешей с секретной солью из `.env`.
По хешу нельзя восстановить человека, но у одного человека он всегда одинаковый, поэтому действия
склеиваются в одну историю. Менеджер работает с номером заявки.

### Атрибуция и ROMI

Три правила движка:

1. **Окно 30 дней** (`ATTRIBUTION_WINDOW_DAYS`). Если человек зашёл по рекламе, а купил позже,
   касание «протухло» и выручку не получает.
2. **Повторные покупки.** Для каждого заказа берутся только касания после предыдущей покупки
   этого клиента: реклама, уже приведшая к первой покупке, за вторую заслуг не получает.
3. **Органика.** Если рекламных касаний в окне нет, выручка не пропадает, а уходит в Organic/Direct.

Модели на примере: реклама в канале A -> через неделю пост в B -> промокод в C -> покупка 10 000 руб.

| Модель | Логика | A | B | C |
|---|---|---|---|---|
| `last` (по умолчанию) | всё последнему касанию | - | - | 10 000 |
| `first` | всё первому | 10 000 | - | - |
| `linear` | поровну | 3 333 | 3 333 | 3 333 |
| `position` | 40% первому, 40% последнему, 20% средним | 4 000 | 2 000 | 4 000 |

ROMI = (приписанная выручка − стоимость) / стоимость. Если задан `ACQUIRING_RATE`, считается ещё
и ROMI по марже. Для своего канала (стоимость 0) ROMI не считается, показывается только воронка.

**Атрибуция не равна инкрементальности.** ROMI показывает, кому приписана уже случившаяся покупка,
а не то, случилась бы она без рекламы. Для настоящего эффекта нужен holdout-эксперимент.

### Что знаем, что оцениваем, чего не видим

| Уровень | Что относится |
|---|---|
| **Знаем** (факты) | оплаты из base.xlsx; заходы по меткам, просмотры и заявки из бота; стоимость и дата размещения из `/newlink` |
| **Оцениваем** (модель) | приписанная выручка, ROMI, CPA; эквайринг по ставке из `.env` - в базе помечен как `rate_estimate` |
| **Не видим** | клики по ссылке без нажатия «Старт» (Telegram их не передаёт); переписку менеджера; клиентов, написавших менеджеру напрямую; источник покупок из base.xlsx; купил бы клиент без рекламы |

### Ограничения
- Первый измеримый шаг - нажатие «Старт», поэтому воронка начинается с заходов, а не с кликов.
- Если клиент написал менеджеру напрямую, источник теряется. Нужна причина заходить через бота
  (каталог, пакеты, промокоды), а менеджер спрашивает номер заявки или «откуда узнали».
- Покупатели из base.xlsx и пользователи бота пока не склеиваются: в выгрузке только обезличенный
  `student_id`. Для склейки бизнесу нужно хешировать username тем же способом, что и бот.
- `.env` и `data/bot.db` в репозиторий не попадают: там токен и данные пользователей.
